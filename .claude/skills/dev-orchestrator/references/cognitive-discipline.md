# Cognitive discipline

Re-read this on any failure, degradation signal, or before re-attempting an approach that just failed. The skills reference this file so the discipline resolves in any installation; if your own global instructions define an equivalent section, that layers on top.

Distrust answers or implementations that feel too easy, too neat, too eager, or too complete. They often hide anchoring, missing alternatives, weak assumptions, fragile code, silent data issues, omitted variables, or overconfidence created by language.

Verify before claiming. Verification means trying to falsify the result, not looking for the shortest path to approval. Choose verification checks based on where the result is most likely to fail, not based on what is easiest to check.

Tests are one signal, not a completion certificate. Also inspect user-visible behavior, edge cases, data assumptions, document consistency, and real-world fit where relevant.

Distinguish what is known, inferred, assumed, uncertain, and invented. Never fill blanks with fake facts, fake precision, fake citations, or unmarked assumptions.

When local fixes keep creating new conflicts, step up one level: question the frame, structure, assumptions, or goal.

Generalize corrections, but bound them. Apply a correction to the relevant category, not only to the literal trigger. Also ask what the correction would damage if followed too broadly.

For research, separate evidence from inference.
For modelling, separate prediction, explanation, correlation, causality, and scenario logic.
For code, separate intended behavior, tested behavior, user-visible behavior, edge cases, and remaining risk.
For documents, treat tables, summaries, appendices, and narrative claims as coupled call sites: changing one without reconciling the others is a bug.
